# Spec: API Core (NestJS)

- **Date:** 2026-07-12
- **Status:** Approved
- **Phase:** 2

## Overview

Phase 2 turns the NestJS walking-skeleton app (`apps/api`) into the real API Gateway/BFF core: Clean Architecture layering, JWT authentication with rotated refresh tokens, user accounts with role-based access, and the product/category catalog with pagination, filtering, Redis caching, and PostgreSQL persistence through Prisma migrations. It also lands the cross-cutting API standards every later phase builds on: versioned routes, validation, rate limiting, Swagger, correlation IDs, structured logging, and centralized error handling.

## Goals

- **Clean Architecture restructure** of `apps/api/src`: `domain/` (entities, domain errors), `application/` (use cases + ports/interfaces), `infrastructure/` (Prisma, Redis, hashing, JWT, config), `presentation/` (controllers, DTOs, guards, filters, interceptors). No business logic in controllers; repositories abstract all data access.
- **Persistence with Prisma**: schema + committed migrations for `User`, `RefreshToken`, `Category`, `Product`; `prisma migrate deploy` runs on API container start; seed script creates the admin user and a small demo catalog.
- **Authentication** (`/api/v1/auth`): public customer registration, login (bcrypt), access JWT (15 min), refresh JWT (7 days) with rotation — refresh tokens stored hashed, old token revoked on use, logout revokes the active refresh token.
- **Authorization**: roles `CUSTOMER` and `ADMIN`; guards enforce authentication and role; catalog writes are ADMIN-only, catalog reads are public.
- **Users**: `GET /api/v1/users/me` (authenticated profile).
- **Catalog**: categories and products CRUD; public list/detail with pagination (`page`, `limit` → `meta`), filtering (category slug, name search, price range) and sorting (`createdAt`, `price`); prices stored as integer cents.
- **Caching** (application-layer `CachePort`, ioredis adapter): product list, product by id/slug, category list; TTL 5 minutes; write operations invalidate the affected keys; cache failures degrade gracefully (never break reads).
- **API standards**: URI versioning `/api/v1/*` (health stays `/api/health`), global `ValidationPipe` (whitelist + transform), standardized success/error envelopes, Swagger/OpenAPI at `/api/docs`.
- **Rate limiting**: global throttling (100 req/min per IP) with a stricter bucket on `/api/v1/auth/*` (10 req/min).
- **Observability**: structured JSON logging (nestjs-pino) with a correlation ID per request (accepts `x-correlation-id` or generates one via `@mini-e-commerce/shared`); global exception filter returns the error envelope with the correlation ID and never leaks stack traces; secrets/passwords/tokens never logged.
- **Environment/Compose**: add a `redis` service (`redis:alpine`, healthcheck) to docker-compose; `api` service gains `DATABASE_URL`, `REDIS_URL`, and JWT env vars and depends on healthy postgres + redis; `.env.example` updated. Dev uses the compose Redis; production points `REDIS_URL` at Upstash (`rediss://`).
- **Shared contracts**: pagination meta, response envelope, and error envelope types added to `@mini-e-commerce/types` (consumed by the storefront in Phase 3).
- **Tests**: unit tests for the critical use cases (register, login, refresh rotation, product create/update with cache invalidation); e2e tests for the auth flow, RBAC enforcement, catalog CRUD, pagination/filtering, and rate limiting.

## Non-Goals

- No orders domain (Phase 3, with the storefront checkout) and no QStash event publishing (Phase 6).
- No stock/inventory data on products — stock belongs to the Go inventory service (Phases 4/6).
- No email verification, password reset, OAuth, or account management beyond `GET /users/me`.
- No image upload — `imageUrl` is a plain string field.
- No Upstash REST client (`@upstash/redis`); the Redis protocol client works for both local and Upstash.
- No admin UI (Phase 7) and no storefront consumption (Phase 3).

## Architecture

```text
presentation/  controllers, DTOs (class-validator), guards (JwtAuthGuard, RolesGuard),
               exception filter, logging/correlation interceptor, Swagger setup
application/   use cases (RegisterUser, LoginUser, RefreshTokens, LogoutUser, GetProfile,
               CRUD + list use cases for products/categories), ports (UserRepository,
               ProductRepository, CategoryRepository, RefreshTokenRepository, CachePort,
               PasswordHasherPort, TokenServicePort)
domain/        entities (User, Product, Category, RefreshToken), enums (UserRole),
               domain errors (EmailAlreadyInUse, InvalidCredentials, ...)
infrastructure/ PrismaService + repository implementations, IoredisCacheAdapter,
               BcryptPasswordHasher, JwtTokenService, typed config module
```

- Request flow: controller → use case (application) → ports → infrastructure adapters. Domain errors are mapped to HTTP responses by the global exception filter.
- Cache-aside in the list/detail use cases: try `CachePort.get`, fall back to repository, `set` with TTL 300s; write use cases call targeted invalidation. Key layout: `products:list:<query-hash>`, `products:id:<id>`, `products:slug:<slug>`, `categories:list`. List invalidation clears `products:list:*` (tracked via a key set or `SCAN`) plus the touched id/slug keys.
- Compose network: api → `postgres:5432` (database `mini_ecommerce`), api → `redis:6379`. Host dev tooling uses `localhost:5433` / `localhost:6380` (the host's own postgres and redis occupy the default ports).

## Data & Contracts

- **Prisma models** (`apps/api/prisma/schema.prisma`):
  - `User`: `id` (uuid), `email` (unique), `passwordHash`, `name`, `role` (`CUSTOMER` | `ADMIN`), timestamps.
  - `RefreshToken`: `id`, `userId` (FK), `tokenHash` (unique), `expiresAt`, `revokedAt?`, `createdAt`.
  - `Category`: `id`, `name` (unique), `slug` (unique), timestamps.
  - `Product`: `id`, `name`, `slug` (unique), `description`, `priceCents` (int), `imageUrl?`, `categoryId` (FK), `isActive` (default true), timestamps.
- **Endpoints** (all under `/api/v1`):
  - `POST /auth/register` (public) · `POST /auth/login` (public) · `POST /auth/refresh` (public, body: refresh token) · `POST /auth/logout` (auth).
  - `GET /users/me` (auth).
  - `GET /categories` (public, cached) · `POST /categories` (ADMIN) · `PATCH /categories/:id` (ADMIN) · `DELETE /categories/:id` (ADMIN).
  - `GET /products` (public, cached; query: `page`, `limit`, `search`, `category`, `minPrice`, `maxPrice`, `sort`) · `GET /products/:idOrSlug` (public, cached) · `POST /products` (ADMIN) · `PATCH /products/:id` (ADMIN) · `DELETE /products/:id` (ADMIN, soft: sets `isActive=false`).
- **Envelopes** (types in `@mini-e-commerce/types`): lists → `{ data: T[], meta: { page, limit, total, totalPages } }`; single → `{ data: T }`; errors → `{ statusCode, error, message, correlationId, timestamp, path }`.
- **Auth contract**: login/refresh return `{ accessToken, refreshToken }`; access JWT carries `sub`, `email`, `role`; TTLs from env (`JWT_ACCESS_TTL=15m`, `JWT_REFRESH_TTL=7d`).
- **Env vars** (`.env.example`): existing Postgres/JWT entries plus `DATABASE_URL`, `REDIS_URL`.
- **Seed**: admin user (`ADMIN_EMAIL`/`ADMIN_PASSWORD` env, defaults documented) + 3 categories / ~12 demo products.

## Acceptance Criteria

- `pnpm turbo run build lint test` passes; api unit + e2e suites pass.
- Prisma migrations apply cleanly to the compose postgres; the api container runs `prisma migrate deploy` on start.
- E2E-proven auth flow: register → login → access a protected route → refresh rotates the token pair (the used refresh token is rejected afterward) → logout revokes.
- RBAC proven: product write as CUSTOMER → 403; as ADMIN → 201.
- Catalog pagination/filtering proven by e2e (page/limit/meta, search, category and price filters).
- Cache proven: second identical product-list request is served from Redis; a product write invalidates it (e2e or integration test against the compose Redis).
- Rate limiting proven: auth endpoint returns 429 after the threshold.
- Swagger UI responds at `/api/docs` documenting every v1 endpoint.
- Error responses follow the envelope, include the correlation ID, and contain no stack traces; request logs are structured JSON carrying the same correlation ID.
- `docker compose up -d --wait` stays fully green with the new `redis` service and api dependencies.
